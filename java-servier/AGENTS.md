# Java 后端代码规则

本规则适用于 `java-servier` 下所有模块，新增和修改代码都要执行。

## 工作流程

- 修改任何文件前，先给出具体方案，等待用户明确同意后再动手。用户对当前方案的同意只授权该方案，不自动授权后续新增工作。
- 不自行创建 Git 提交。只有用户明确要求提交时才能执行 `git commit`。

## 注释与 Javadoc

- 所有公开或受保护的 Java 类型、构造器和方法必须有 Javadoc。公开的 record 组件、枚举值和常量也必须说明业务含义。
- 所有类的成员变量都必须有 Javadoc，包括 `private` 字段、常量和测试类字段。说明字段的业务含义、来源或约束，避免只重复变量名。
- Javadoc 第一段写清职责或行为，不复述方法名。参数用 `@param`，有返回值用 `@return`，需要调用者处理的异常用 `@throws`。泛型参数用 `@param <T>`。
- 优先使用中文注释；标识符、协议字段、URL 路径和技术术语保持原文。使用 `{@code ...}` 标记代码，使用 `{@link ...}` 关联相关类型。
- `kfcapi` 的公开调用方法要注明上游域名/接口、HTTP 方法、APK 证据文件，以及尚未验证的参数、鉴权或域名归属。不能把候选接口写成已经联调通过。
- 对复杂分支和安全边界写必要的行内注释，说明原因与约束；不写逐行翻译代码的注释。改动行为时同步更新注释。
- 不在注释、示例或日志中记录密钥、token、手机号等真实敏感值。

## YAML 配置注释

- `server/src/main/resources/application.yml` 中每个配置分组和每个叶子配置项都必须有中文注释，写明用途、默认值或覆盖变量、开关影响以及必要的安全约束。
- 新增、移动或修改 YAML 配置时必须同步维护相邻注释；不得留下无注释配置，也不得在注释中重复或泄露密钥、token、手机号等真实敏感值。
- 敏感明文配置的注释只说明其用途和风险，不复述实际值；提交、推送或分享代码前按工作区安全规则迁回本机忽略配置。

## DTO、实体与工具库

- `db` 实体和传输数据类（请求 DTO、`param`、`vo`、响应 DTO、内部上下文）使用成员变量与 Lombok `@Data`，不要新增 record 作为 DTO；需要按字段赋值时保留有 Javadoc 的无参构造器。实体字段仍需逐项写 Javadoc。
- 含手机号、验证码、token、支付串或设备标识的类使用 `@ToString.Exclude` 避免 Lombok 自动输出敏感字段；不要在业务日志中打印整个对象。
- 优先使用已引入的 Hutool 处理常见字符串、集合和标识操作；密码学实现、签名序列化和安全随机数继续遵守已验证协议与 JDK 安全 API。
- 项目已引入 Fastjson2；新增 JSON 辅助处理优先使用 Fastjson2。已验证的 Jackson 协议序列化与签名链路不要仅为换库而改动；改动时必须核对实际发出的 JSON 字节与签名一致。
- 仅在用户当次授权的手动真实登录测试中，允许测试专用拦截器向本机控制台打印完整 HTTP 请求和响应报文以便核对。不得把含手机号、验证码、token、密钥或设备标识的控制台输出复制到聊天、提交到 Git 或上传第三方；普通测试与生产服务保持关闭。
- `kfc_user` 中需要持久化的加密业务值同时保留明文列和对应密文列，以便本机核对；手机号和 token 按此规则存储。短信验证码只用于当次登录，不持久化。新增同类持久化字段时须成对建列，并限制明文字段出现在日志或对外响应中。

## 品牌 API 模块边界

- `basicapi` 只保存跨品牌通用的 HTTP 传输、响应、异常、品牌枚举和鉴权扩展接口，不得放入具体品牌域名、签名、加密、请求字段或 DTO。
- `kfcapi` 只保存 KFC 代码，`phhsapi` 只保存 PHHS 代码；两个品牌模块只能依赖 `basicapi` 等公共模块，禁止互相依赖或复用对方命名的协议实现。
- 品牌上游按真实域名建立去掉点号的全小写包，并统一在其下使用 `api`、`param`、`support`、`vo` 分层。例如 `applogin.phdapp.cn` 必须放在 `phhsapi/.../apploginphdappcn/{api,param,support,vo}`，不得把域名接口类平铺在品牌根包。
- 品牌根包只保留该品牌跨域名共用且命名明确的类型，例如 `KfcUpstream`、`PhhsUpstream`。新增品牌或域名时同步新增独立 Maven 模块或域名包、上游枚举项、配置、协议测试和 README 说明。

## 手工 SQL 与注释

- 新建表必须使用 MySQL 原生 `COMMENT` 写清表用途，并为每个字段写业务含义、来源或约束；修改已有表新增字段时也必须写字段 `COMMENT`。这些注释应能通过 `SHOW CREATE TABLE` 或 `information_schema` 查看，不能仅用 SQL 行注释代替。
- 数据库结构由用户手动执行 SQL；Java 服务启动时不得自动建表、改表或引入 Flyway。现有 `db/src/main/resources/db/migration/` 中的 V1–V4 文件保留为需按顺序执行的 SQL 脚本；后续新增脚本要写明执行前提与顺序，不修改已人工执行的历史脚本。

## 执行方式

完成修改后在本目录运行 `mvn -s .mvn/settings.xml clean verify`。构建中的 Javadoc 和 Checkstyle 字段注释检查必须通过；不得通过关闭检查、忽略警告或跳过模块来绕过。接口尚未联调时，在 Javadoc 和 README 中明确标为待验证。
